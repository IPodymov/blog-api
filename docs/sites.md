# Несколько сайтов на одном API

Один экземпляр API обслуживает любое количество сайтов-блогов. Каждый сайт —
отдельный изолированный «арендатор» (tenant): у него свои пользователи, статьи,
комментарии, лайки, теги, статистика и токены. Данные одного сайта не видны и
не изменяемы с другого.

## Как клиент указывает сайт

Каждый запрос к `/api/v1/*` обязан содержать заголовок `X-Site-Key` с ключом
сайта:

```sh
curl http://localhost:8080/api/v1/articles -H 'X-Site-Key: my-blog'
```

| Ситуация | Ответ |
| --- | --- |
| Заголовок не передан | `400`, `code: "site_required"` |
| Ключ в неверном формате или такого сайта нет | `400`, `code: "unknown_site"` |
| ID статьи, комментария или пользователя принадлежит другому сайту | `404`, как будто ресурса нет |
| Access-токен выдан на другом сайте | `401`, `code: "invalid_token"` |
| Refresh-токен другого сайта в `/auth/refresh` или `/auth/logout` | `401` для refresh, `204` без эффекта для logout; сессия на «родном» сайте не отзывается |

`/health`, `/ready`, `/docs`, `/openapi.yaml` и `/` заголовок не требуют.
Preflight-запрос `OPTIONS` тоже проходит без него; `X-Site-Key` разрешён в
`Access-Control-Allow-Headers`.

Ключ сайта — **публичный идентификатор, а не секрет**: он виден в коде
фронтенда. Изоляция обеспечивается не секретностью ключа, а тем, что все
запросы и токены привязаны к сайту на уровне SQL и ограничений БД.

Пример клиента в браузере:

```js
const API = 'https://api.example.com/api/v1';
const SITE_KEY = 'my-blog';

export function api(path, { token, headers, ...init } = {}) {
  return fetch(API + path, {
    ...init,
    credentials: 'include', // для гостевой cookie просмотров
    headers: {
      'X-Site-Key': SITE_KEY,
      ...(token ? { Authorization: `Bearer ${token}` } : {}),
      ...headers,
    },
  });
}
```

## Что изолировано

| Данные | Правило |
| --- | --- |
| Пользователи | `username` и `email` уникальны **в пределах сайта**. Один и тот же email на двух сайтах — два независимых аккаунта со своими паролями и профилями. |
| Вход и токены | Логин ищет пользователя только на текущем сайте. Access/refresh-токены действуют только на сайте, где выданы. |
| Роли | Роль действует только на своём сайте: автор на одном сайте остаётся обычным пользователем на другом. Администратор модерирует только свой сайт. |
| Статьи | `slug` уникален в пределах сайта: разные сайты могут иметь статьи с одинаковым slug. Списки, поиск, фильтры, чтение по ID и slug — только статьи текущего сайта. |
| Комментарии и лайки | Можно оставить только к статье своего сайта и только пользователю этого сайта; это закреплено составными FK в БД. |
| Теги | `GET /tags` возвращает только теги опубликованных статей текущего сайта. |
| Профили и статистика | `/users/{id}`, `/me/*`, статистика статей — только в пределах сайта. |
| Просмотры | Регистрируются только для статей текущего сайта. |
| `canonical_url` | Строится из `public_url` сайта: `{public_url}/articles/{slug}`. |

### Что общее

- Нумерация ID общая для всех сайтов, поэтому ID на одном сайте идут не
  подряд. Это не раскрывает данных: чужой ID всегда даёт `404`.
- Справочник имён тегов общий (только строки вида `go`), но выдача тегов
  фильтруется по сайту.
- Гостевая cookie `blog_visitor` общая для домена API; дедупликация просмотров
  всё равно ведётся по каждой статье отдельно.
- Rate limit, `VISITOR_SECRET` и прочая конфигурация — общие для экземпляра API.
- CORS открыт для всех: запросы принимаются с любого `Origin`, настраивать
  список origins на сервере не нужно. Какие статьи показать, определяет клиент
  значением `X-Site-Key`.
- Сервер не связывает `Origin` с ключом сайта: любой origin может передать любой
  ключ. Это не нарушает изоляцию, потому что ключ публичный, а изменение данных
  и доступ к черновикам требуют токена конкретного сайта. Опубликованные статьи
  сайта может прочитать любой, кто знает его ключ.

## Добавление сайта

Сайты создаёт оператор БД (так же, как назначается администратор):

```sql
INSERT INTO sites(key, name, public_url)
VALUES ('my-blog', 'Мой блог', 'https://my-blog.example');
```

- `key` — формат slug: `[a-z0-9]+(-[a-z0-9]+)*`, до 64 символов, уникален.
- `name` — произвольное название для оператора, до 200 символов.
- `public_url` — адрес сайта для `canonical_url`, без query/fragment. Пустая
  строка означает «использовать `PUBLIC_SITE_URL` из окружения».

Затем укажите этот ключ в конфигурации фронтенда. Менять настройки API или
передеплоивать его не нужно.

Назначить администратора сайта:

```sql
UPDATE users SET role='admin'
WHERE username='your_admin' AND site_id=(SELECT id FROM sites WHERE key='my-blog');
```

Список сайтов: `SELECT id, key, name, public_url, created_at FROM sites;`

## Роли

| Роль | Что может |
| --- | --- |
| `user` | Выдаётся при регистрации. Комментарии и лайки; создавать статьи нельзя. |
| `author` | То же, плюс создание статей и управление своими статьями. |
| `admin` | То же, плюс модерация всех статей и комментариев сайта. |

Регистрация открыта, а ключ сайта публичный, поэтому аккаунт может создать любой.
Роль защищает публикацию: без `author` или `admin` запросы `POST /articles` и
`PATCH /articles/{id}` получат `403`, `code: "author_role_required"`. Удалить
свою статью можно и после снятия роли.

Роли назначает оператор БД. Новая роль действует сразу, в том числе для уже
выданных токенов:

```sql
UPDATE users SET role='author'
WHERE username='your_author' AND site_id=(SELECT id FROM sites WHERE key='my-blog');
```

## Локальная разработка

Локально действуют те же правила, что и в production: изоляцию определяет
`X-Site-Key`, а не домен или порт. Все сайты работают с одним API
(`localhost:8080`) и одной локальной БД, поэтому каждому фронтенду нужен свой
ключ. Миграции создают только сайт `default`, остальные добавьте сами.

Пример для двух фронтендов на портах 3000 и 3001:

```sh
# 1. Поднимите БД и примените миграции:
docker compose up -d db
make migrate
# 2. Создайте сайты; public_url нужен, чтобы canonical_url вёл на свой порт:
docker compose exec db psql -U blog -d blog -c "INSERT INTO sites(key,name,public_url) VALUES ('blog-a','Блог A','http://localhost:3000'),('blog-b','Блог B','http://localhost:3001')"
# 3. Запустите API:
make run
```

Затем в конфигурации каждого фронтенда задайте свой ключ, например
`X-Site-Key: blog-a` и `X-Site-Key: blog-b`.

Что учитывать:

- **Один ключ на два фронтенда объединяет их данные.** Сервер не связывает
  `Origin` с ключом, поэтому фронтенд на порту 3001 с ключом `blog-a` получит
  данные сайта `blog-a`. Не задавайте ключ одним общим значением на все проекты.
- **Забытый ключ не приводит к смешиванию данных.** Запрос без заголовка получит
  `400 site_required` и не попадёт в сайт `default`.
- **Cookie браузера не разделяются по портам.** `localStorage` у
  `localhost:3000` и `localhost:3001` раздельный, а cookie с одним именем общие.
  Если фронтенды хранят токен в cookie на своём домене, дайте им разные имена.
  Иначе один сайт перезапишет токен другого, и API ответит `401`. Гостевая
  cookie API `blog_visitor` общая, но это безопасно: просмотры считаются по
  каждой статье отдельно.
- **Rate limit общий для всех локальных сайтов,** потому что считается по
  IP-адресу. На всех приходится 10 запросов `/auth/*` в минуту; после этого API
  ответит `429`. Лимит сбрасывается через минуту или при перезапуске API. Ключ
  сайта в счётчик намеренно не входит: иначе лимит можно было бы обойти, перебирая
  ключи.
- **Swagger UI (`/docs`)** запрашивает `X-Site-Key` в каждой операции, которую
  вы запускаете через «Try it out».

Сбросить данные одного локального сайта можно, не затрагивая остальные, —
см. раздел «Удаление сайта». Команда `docker compose down -v` удалит локальную
БД всех сайтов целиком.

## Удаление сайта

Удаление необратимо. Сначала удаляются пользователи сайта — вместе с ними
каскадно удаляются их статьи, комментарии, лайки, сессии и статистика, — затем
сама запись сайта:

```sql
BEGIN;
DELETE FROM users WHERE site_id=(SELECT id FROM sites WHERE key='my-blog');
DELETE FROM sites WHERE key='my-blog';
COMMIT;
```

Прямое `DELETE FROM sites` при наличии пользователей завершится ошибкой FK —
это защита от случайного удаления.

## Обновление существующей установки

Миграция `002_sites.sql` создаёт сайт с ключом `default` и переносит в него все
существующие данные. Его `public_url` пуст, поэтому `canonical_url` продолжает
строиться из `PUBLIC_SITE_URL`. После деплоя **существующий фронтенд должен
начать отправлять `X-Site-Key: default`**, иначе он получит `400 site_required`.
Выданные ранее токены продолжают работать на сайте `default`.

Ключ и адрес сайта можно изменить:

```sql
UPDATE sites SET key='main-blog', public_url='https://blog.example' WHERE key='default';
```

### Обновление до ролей

Миграция `003_author_role.sql` никого не повышает: нельзя отличить настоящих
авторов от посторонних, которые зарегистрировались раньше. После неё все
пользователи с ролью `user` теряют возможность создавать и редактировать статьи,
поэтому сразу назначьте `author` нужным аккаунтам. Уже опубликованные статьи
остаются на сайте. Проверьте, кто успел их создать:

```sql
SELECT s.key, u.username, u.email, count(*) AS articles
FROM articles a JOIN users u ON u.id=a.author_id JOIN sites s ON s.id=a.site_id
WHERE u.role='user'
GROUP BY s.key, u.username, u.email ORDER BY s.key, articles DESC;
```

## Как это устроено

- Таблица `sites`; столбец `site_id` есть у `users`, `articles`, `comments` и
  `likes`.
- Уникальность: `(site_id, username)`, `(site_id, email)`, `(site_id, slug)`.
- Составные внешние ключи `(author_id, site_id) → users(id, site_id)`,
  `(article_id, site_id) → articles(id, site_id)` и
  `(user_id, site_id) → users(id, site_id)` не позволяют БД сохранить статью,
  комментарий или лайк, связывающий разные сайты, даже при ошибке в коде.
- HTTP-middleware маршрутов `/api/v1` определяет сайт по `X-Site-Key` и только
  затем проверяет bearer-токен в пределах этого сайта. Все SQL-запросы
  репозитория фильтруются по `site_id`.
