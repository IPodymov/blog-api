# Blog REST API

Развёртывание API в Vercel с PostgreSQL Neon: [docs/vercel.md](docs/vercel.md).

Рабочий модульный монолит на Go: PostgreSQL, chi, pgx, net/http, slog. Контракт — [openapi.yaml](api/openapi.yaml), Swagger UI — `/docs`; описание всех ручек, параметров и тел запросов — [docs/api.md](docs/api.md). API работает с Markdown; веб-интерфейс блога не входит в проект. Каноническая ссылка ведёт на настроенный публичный сайт, который должен реализовать страницу `/articles/{slug}`.

## Быстрый запуск

Нужны Docker Engine + Compose. Для локального Go: Go 1.27.2+, для проверки OpenAPI: Node.js 22.12+ и Python 3.

```sh
cp .env.example .env
# В .env задайте случайные значения; например получите их командами:
openssl rand -hex 24  # POSTGRES_PASSWORD
openssl rand -hex 32  # VISITOR_SECRET
# В локальном DATABASE_URL используйте тот же пароль POSTGRES_PASSWORD.
docker compose up --build -d
curl http://localhost:8080/ready
# Откройте http://localhost:8080/docs
```

Compose ждёт готовности PostgreSQL, запускает идемпотентные миграции и затем API. Внутренний `DATABASE_URL` Compose собирает сам. Если локальный порт 5432 занят, задайте `POSTGRES_PORT` и используйте тот же порт в локальном `DATABASE_URL`. Для локальной разработки:

```sh
docker compose up -d db
make migrate
make run
```

`make run` собирает и запускает бинарник API напрямую. Для остановки нажмите `Ctrl+C` в этом терминале: сервер закроет порт 8080 и завершит активные запросы (до 15 секунд). При превышении таймаута оставшиеся соединения закрываются принудительно. Не завершайте только родительский процесс `go run`: его дочерний API может продолжить работу.

Команды API, миграций и очистки автоматически читают `.env` из текущей рабочей директории. Запускайте их из корня проекта. Уже заданные переменные окружения имеют приоритет; поддерживаются простые `KEY=value` и значения в кавычках без shell-подстановок. Не передавайте секреты в репозиторий; `.env` исключён. Для production используйте HTTPS, `COOKIE_SECURE=true`, защищённую PostgreSQL-сеть/TLS (`sslmode=verify-full`) и реальные CORS origins. `VISITOR_SECRET` обязателен, минимум 32 байта; его смена инвалидирует гостевые cookie и дедупликацию прежних гостей. Секреты авторизации хранятся в БД только как SHA-256 случайных токенов.

## Проверки

```sh
npm ci --ignore-scripts
make check                    # OpenAPI, сверка маршрутов, gofmt, go vet, unit/HTTP + race
make build
# При запущенном сервере также можно проверить настоящий HTTP:
python3 scripts/smoke.py http://localhost:8080
# Отдельная тестовая БД; не production. Тест создаёт случайную schema и удаляет её.
docker run -d --name blog-api-test-db -e POSTGRES_PASSWORD=blogtest \
  -p 127.0.0.1:55432:5432 postgres:18.6-alpine
TEST_DATABASE_URL='postgres://postgres:blogtest@127.0.0.1:55432/postgres?sslmode=disable' make integration
docker rm -f blog-api-test-db
```

Интеграционный тест запускает настоящие миграции, HTTP-обработчики и SQL-репозитории. Есть проверки приватности, списков профилей, комментариев и ответов, конкурентных лайков/просмотров/редактирования, дедупликации, UTC-дней и нулевых дней, снятия публикации и каскадного удаления, ротации/повторного использования/отзыва токенов и администраторской модерации. Unit-тесты проверяют правила доступа, диапазоны дат, валидацию статей, гостевые подписи и PATCH/ETag.

`api/openapi.yaml` сериализован как JSON — это валидный YAML 1.2 и OpenAPI 3.1. Можно напрямую использовать для генерации клиентов. Источник спецификации: `scripts/generate_openapi.py`; после изменений запускайте `python3 scripts/generate_openapi.py`. Redocly 2.62.1 проверяет спецификацию и примеры, дополнительный скрипт сверяет маршруты и детерминированную генерацию. Node.js нужен только разработчикам для проверки контракта, не приложению. `/docs` загружает фиксированную версию Swagger UI через CDN, поэтому для интерфейса документации нужен интернет; сам контракт доступен локально по `/openapi.yaml`.

## Архитектура

Подробности и ER-диаграмма: [docs/architecture.md](docs/architecture.md).

```text
api/                 OpenAPI-контракт, встроенный в бинарник (go:embed)
cmd/api/             запуск, подключения, сигналы, HTTP timeouts
cmd/migrate/         миграции с advisory lock и проверкой checksum
cmd/maintenance/     повторяемая очистка истёкших служебных данных
internal/config/     env-конфигурация и проверка её значений
internal/domain/     DTO/сущности, ошибки, правила доступа и периода
internal/service/    бизнес-правила, права, bcrypt, токены, canonical URL
internal/repository/ параметризованный SQL, транзакции и конкурентность
internal/httpapi/    chi, обработчики, decode, CORS, rate limit, HTTP errors
migrations/          встроенные SQL-миграции
scripts/             генерация и проверка OpenAPI, Vercel build, smoke-тест
docs/                API, архитектура, Vercel, отчёт о проверке
.github/workflows/   CI: lint, unit, интеграционные тесты, контракт, Docker
```

Зависимости: HTTP → service → repository → pgx; все слои используют domain. Инфраструктура создаёт конкретные зависимости. Нет микросервисов, Redis, очередей или фонового пересчёта. Репозиторий — небольшой конкретный адаптер PostgreSQL; заменять его fake-БД ради тестов SQL не требуется. Бизнес-инварианты тестируются отдельно, транзакционные — на настоящем PostgreSQL.

HTTP-слой проверяет JSON, размер тела, query/path и `If-Match`. Сервис проверяет текст, статусы, принадлежность, доступ к черновикам и статистике. Репозиторий объединяет изменения в транзакции, БД закрепляет FK/UNIQUE/CHECK. Доменные ошибки отображаются в HTTP; неизвестные ошибки становятся 500 без SQL или секретов в ответах. Все ошибки:

```json
{"error":{"code":"validation_failed","message":"Некорректные данные","details":{"title":"Недопустимая длина"},"request_id":"server-generated-id"}}
```

## Контракт и решения

Префикс `/api/v1`. Полный список схем, параметров, примеров и статусов находится в OpenAPI.

| Маршрут | Права / назначение |
|---|---|
| `POST /auth/register` | Гость; регистрация с ролью user, токены |
| `POST /auth/login` | Гость; email/password, токены |
| `POST /auth/refresh` | Refresh в JSON; одноразовая ротация |
| `POST /auth/logout` | Refresh в JSON; отзыв семейства, 204 |
| `GET /users/{user_id}` | Все; публичный профиль и опубликованные показатели |
| `GET /users/{user_id}/articles` | Все; опубликованные статьи автора |
| `GET /me`, `PATCH /me` | Владелец аккаунта; email/роль, редактирование профиля |
| `GET /me/articles` | Владелец; опубликованные и черновики, `status` |
| `GET /me/statistics` | Владелец; сводка, UTC-дни, top 5 за период |
| `GET /me/statistics/articles` | Владелец; показатели статей, пагинация |
| `GET /articles` | Все; публикации, `q`, `author_id`, `tag`, `sort` |
| `POST /articles` | Пользователь; создание, по умолчанию draft |
| `GET /articles/{article_id}` | Все для публикаций, автор/admin для draft |
| `GET /articles-by-slug/{slug}` | Все; только опубликованная статья |
| `PATCH /articles/{article_id}` | Автор/admin; обязательный `If-Match` |
| `DELETE /articles/{article_id}` | Автор/admin; `If-Match`, физическое удаление |
| `POST /articles/{article_id}/views` | Все; отдельное событие открытия без тела |
| `GET /articles/{article_id}/statistics` | Автор/admin; подробная аналитика |
| `GET /articles/{article_id}/comments` | Читатели статьи; плоский список с parent_id |
| `POST /articles/{article_id}/comments` | Пользователь; только публикация |
| `PATCH /comments/{comment_id}` | Автор комментария/admin |
| `DELETE /comments/{comment_id}` | Автор комментария/admin; tombstone |
| `PUT`, `DELETE /articles/{article_id}/like` | Пользователь; идемпотентная установка/снятие |
| `GET /tags` | Все; только теги опубликованных статей |

`GET /` (редирект на `/docs`), `GET /health`, `GET /ready`, `GET /docs`, `GET /openapi.yaml` находятся вне API-префикса. Все публичные маршруты принимают необязательный bearer-токен; если он передан и недействителен, ответ 401. Публичный профиль всегда публичный, даже при запросе владельца. Приватные поля доступны только через `/me`. Администратор назначается оператором БД, не через регистрацию:

```sql
UPDATE users SET role='admin' WHERE username='your_admin';
```

ID — положительные bigint. Статья содержит публичного автора, все текстовые поля и счётчики. `canonical_url` равен `PUBLIC_SITE_URL/articles/{slug}` только при публикации, иначе null. Клиент распространяет эту ссылку самостоятельно; изменение slug меняет ссылку, старый slug не перенаправляется.

Пагинация offset: `page=1`, `page_size=20`, максимум 100, page максимум 100000. Ответ `{items,page,page_size,total}`. Для статей сортировка по убыванию `published_at` (default), `views`, `popularity`, `created_at`, затем ID DESC. Формула популярности: `views + 5*likes + 3*comments`; это простая прозрачная формула без обещания трендового рейтинга. Поиск — PostgreSQL full text с конфигурацией simple, фильтр `tag` точный (один тег). В `/me/articles` `status` необязателен. Комментарии — ID ASC, теги — name ASC. Сортировка стабильна при равных значениях; обновления данных между запросами могут перемещать записи между страницами. Для небольшого блога offset проще; при большом количестве данных можно добавить keyset pagination отдельной версией контракта.

`PATCH`: отсутствующее поле сохраняется; null запрещён, пустая строка очищает description/bio/avatar/display_name, `[]` очищает теги. Заголовок, slug, content и комментарий не могут быть пустыми. Неизвестные поля JSON запрещены. `parent_id:null` допустим только при создании комментария и означает корневой комментарий. Версия статьи возвращается как `version` и `ETag: "1"`; обновление увеличивает её атомарно. Изменение счётчиков не меняет версию содержимого. PATCH/DELETE без `If-Match` дают 428, с устаревшим — 412.

Текст: title до 200 символов, description до 500, Markdown до 100000, комментарий до 5000, bio до 2000, display_name до 100. Slug: `[a-z0-9]+(-[a-z0-9]+)*`, до 200; username: `[a-z0-9_]`, 3..32; email нормализуется в нижний регистр. Пароль 12..72 байта UTF-8, bcrypt cost 12. Максимум 10 уникальных тегов, каждый до 40 символов в формате slug. Аватар — HTTPS URL до 2048 символов либо пустая строка; сервер URL не скачивает.

Ответы на комментарии имеют максимум один уровень (depth 0 или 1), parent должен принадлежать той же статье и быть активным корневым комментарием. Удаление очищает текст и помечает `deleted=true`, сохраняя ID и ответы. Tombstones присутствуют в списке, но не в счётчике комментариев. Удалённый комментарий нельзя редактировать. Автор комментария может удалить его и после снятия статьи с публикации.

## Учёт просмотров и аналитика

GET статьи никогда не увеличивает счётчик. Клиент отправляет POST `/articles/{id}/views` после фактического открытия. Ответ `{counted:true|false}`. Счётчики обновляются сразу после commit, асинхронной задержки нет.

Авторизованная идентичность — ID пользователя. Гостевая — случайный 256-битный идентификатор, выданный сервером в подписанном cookie `blog_visitor`; произвольному cookie/телу сервер не доверяет. В `view_dedup` хранится HMAC идентичности с серверным секретом, ID статьи и UTC-время последнего **учтённого** просмотра. Публичные ответы не содержат этих значений. В дневном агрегате хранятся только ID статьи, UTC-дата и количество.

Один просмотр на посетителя и статью за `VIEW_INTERVAL`, по умолчанию 30m. Дубль не продлевает окно. После завершения окна следующий запрос учитывается. Транзакция блокирует статью, проверяет публикацию, исключает автора и всех администраторов, условно обновляет дедупликацию и увеличивает дневной агрегат. Регистрация просмотра и снятие публикации сериализованы одной блокировкой. Повторная отправка в окне идемпотентна; retry спустя окно трактуется как новое открытие. Это счётчик просмотров, **не уникальных посетителей**. Уникальные посетители не вычисляются.

Cookie: HttpOnly, SameSite=Lax, Path=/api/v1, без Domain, Max-Age=1 год, Secure по `COOKIE_SECURE` (production true). Для другого origin того же site нужен разрешённый `CORS_ORIGINS` и `fetch(...,{credentials:'include'})`. Для cross-site размещения Lax/ограничения браузеров могут блокировать cookie; размещайте сайт/API на одном site или за same-origin proxy. Удаление cookie, другое устройство/браузер, переход между гостевым и авторизованным режимом создают разные идентичности. Первые одновременные запросы гостя без cookie могут учитываться отдельно. Подпись запрещает подделку идентичности, но не запрещает злоумышленнику удалять cookie; базовый rate limit снижает накрутку, полной защиты от ботов нет.

`date_from`/`date_to`: YYYY-MM-DD, UTC, обе даты включительны; математически `[date_from 00:00Z, date_to+1 00:00Z)`. По умолчанию последние 30 календарных дней включая сегодня. Можно задать одну границу, другая остаётся значением по умолчанию. Обратный диапазон, будущая дата, несуществующая дата и период длиннее `MAX_STATISTICS_DAYS` (default 366) дают 422. Daily всегда содержит каждый день диапазона, даже с 0.

Личная сводка и список учитывают все существующие свои статьи, в том числе снятые с публикации. Сводка возвращает опубликованные/черновики, просмотры за всё время и за период, текущие лайки/комментарии, daily и top 5 по просмотрам периода (при отсутствии просмотров top содержит статьи с нулями). `/me/statistics/articles`: сортировка `views_period` (default), `views`, `likes`, `comments`, `published_at`, ID DESC; до 100 записей. Статистика отдельной статьи доступна автору/admin; у неё такие же границы, daily, просмотры all-time/period и текущие likes/comments. Без статей: суммы 0, items/top пустые, дни с нулями.

Снятие публикации сохраняет накопленные данные в личной аналитике и исключает статью из публичных списков/сводок. Повторная публикация сохраняет историю просмотров, выставляет новую published_at. Удаление статьи физически удаляет связанные агрегаты/лайки/комментарии, поэтому личные суммы и period totals уменьшаются. Снятие лайка/удаление комментария сразу уменьшает текущий счётчик; событий этих действий не храним и историческую динамику не обещаем. Публичный профиль агрегирует только статьи со статусом published.

Дневные агрегаты сохраняются на всё время жизни статьи. Детальные события не сохраняются: дневные данные — источник истины, из них пересчитываются all-time просмотры; дедупликация — только кратковременное служебное состояние. Если дневные агрегаты повреждены, восстановление возможно из резервной копии PostgreSQL, не из удалённых событий. Лайки/комментарии/популярность вычисляются из актуальных таблиц, отдельные кешированные счётчики не хранятся.

```sh
# Запускайте ежедневно через cron/планировщик оператора:
docker compose run --rm --no-deps api /app/maintenance
# либо с экспортированными env:
make maintenance
```

Очистка в одной транзакции удаляет дедупликацию старше настроенного окна, истёкшие access-токены и истёкшие семейства сессий со всеми refresh-токенами. Повторный запуск безопасен. При сбое транзакция откатывается; повторите команду. На correctness очистка не влияет, только на объём БД. До истечения семейства использованные refresh-хеши сохраняются для обнаружения повторного использования. Изменение VIEW_INTERVAL на больший интервал после очистки старого состояния не может восстановить удалённую дедупликацию.

## Безопасность и эксплуатация

Access — случайный непрозрачный bearer-токен с TTL 15m (настраивается, максимум 1h, меньше REFRESH_TTL). Refresh — случайный токен с одноразовой ротацией и абсолютным сроком семейства 30 дней. Проверка access обращается к PostgreSQL и видит logout/replay/revocation сразу. Refresh-запросы клиент сериализует: повторное использование уже использованного токена отзывает всё семейство, даже если причиной был retry после потери ответа. Токены возвращаются только в ответах авторизации; публичные сущности используют отдельные DTO. Клиент хранит их безопасно и не вставляет в URL. Cookie для авторизации не используется, поэтому API не опирается на автоматически прикладываемые браузером полномочия и отдельный CSRF-токен не нужен. XSS у клиента остаётся существенным риском.

Markdown хранится как текст. Клиент отключает raw HTML, санитизирует сгенерированный HTML, запрещает `javascript:` URLs, использует CSP и выводит profile/comment text через безопасные текстовые DOM API. Сервер не делает доверенный HTML из Markdown.

Rate limiting в памяти процесса: общие запросы 300/мин, auth 10/мин, views 60/мин на сетевой адрес соединения. IP используется только как SHA-256 ключ в ограниченном map на одну минуту, не сохраняется в БД/логах аналитики. `X-Forwarded-For` не доверяем. За proxy многие пользователи могут делить один лимит: внешний gateway может ограничивать клиентов отдельно; для нескольких реплик общий лимит также ставится на gateway. Redis для одного экземпляра не нужен. Лимит сбрасывается после рестарта; это базовая защита, не антифрод-платформа. Список разрешённых CORS origins точный, wildcard не поддерживается. При недопустимом Origin — 403. Тело до 512 KiB, SQL параметризован, имена сортировок выбираются из allowlist.

HTTP timeouts: headers 5s, read 15s, write 20s, idle 60s; обработчики получают context с deadline 10s. SIGINT/SIGTERM дают 15s для graceful shutdown. `/health` проверяет процесс, `/ready` — соединение PostgreSQL (2s). Логи JSON slog содержат request_id, метод и duration; нет request body, паролей, токенов, URL/query, IP и текстов SQL-ошибок. Клиент получает `X-Request-ID`; невалидный Authorization даёт 401 даже на публичном маршруте. Успешные ответы API имеют `Cache-Control: no-store` для предотвращения кеширования приватных ответов.

Бэкап PostgreSQL обязателен для сохранения дневной истории; автоматические резервные копии/метрики развёртывания зависят от окружения. Миграции запускаются отдельным процессом до API, под advisory lock и с checksum. Предоставлена начальная forward-only миграция; откат схемы — восстановление резервной копии или новая компенсирующая миграция.

## Примеры curl

```sh
BASE=http://localhost:8080/api/v1
curl -sS "$BASE/auth/register" -H 'Content-Type: application/json' \
  -d '{"username":"alice","email":"alice@example.org","password":"example-password-2026"}'
# Сохраните значения из ответа вручную; не добавляйте токены в репозиторий.
ACCESS='YOUR_ACCESS_TOKEN'
REFRESH='YOUR_REFRESH_TOKEN'
curl "$BASE/me" -H "Authorization: Bearer $ACCESS"
curl -i "$BASE/articles" -H "Authorization: Bearer $ACCESS" \
  -H 'Content-Type: application/json' \
  -d '{"title":"Первый пост","slug":"first-post","description":"Знакомство","content":"# Привет","tags":["go"],"status":"draft"}'
# Для первого созданного ID; подставьте фактический ID и ETag:
curl -X PATCH "$BASE/articles/1" -H "Authorization: Bearer $ACCESS" \
  -H 'Content-Type: application/json' -H 'If-Match: "1"' -d '{"status":"published"}'
curl "$BASE/me/articles?status=published" -H "Authorization: Bearer $ACCESS"
curl "$BASE/me/statistics" -H "Authorization: Bearer $ACCESS"
curl "$BASE/articles-by-slug/first-post"
# Гость: сохраняйте cookie между вызовами; повтор внутри окна counted=false.
curl -c /tmp/blog-cookies -b /tmp/blog-cookies -X POST "$BASE/articles/1/views"
# Другой зарегистрированный пользователь:
OTHER_ACCESS='OTHER_USER_ACCESS_TOKEN'
curl -X PUT "$BASE/articles/1/like" -H "Authorization: Bearer $OTHER_ACCESS"
curl "$BASE/articles/1/comments" -H "Authorization: Bearer $OTHER_ACCESS" \
  -H 'Content-Type: application/json' -d '{"content":"Хорошая статья!"}'
curl -X DELETE "$BASE/articles/1/like" -H "Authorization: Bearer $OTHER_ACCESS"
curl "$BASE/auth/refresh" -H 'Content-Type: application/json' \
  -d "{\"refresh_token\":\"$REFRESH\"}"
# После refresh для выхода нужен НОВЫЙ refresh_token из ответа.
curl "$BASE/auth/logout" -H 'Content-Type: application/json' \
  -d '{"refresh_token":"NEW_REFRESH_TOKEN"}'
```

Результаты выполненных проверок: [docs/verification.md](docs/verification.md).
